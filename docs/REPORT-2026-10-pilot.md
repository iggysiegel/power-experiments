# Report

How much energy does one server use to serve a large language model, and how
does that energy change with the work it is asked to do?

## Summary

We served Qwen3.8-27B with vLLM on one H100 GPU and measured the GPU and the
whole server while running three kinds of synthetic traffic. The main
findings, on the GPU:

- **Keeping the model loaded costs 29 W.** The GPU draws 64 W with the model
  stopped and 93 W with it loaded and waiting. Starting the model costs 4.1 kJ
  and takes 78 s, so stopping it pays off after about 140 s unused.
- **Output tokens cost far more than input tokens.** Reading input costs about
  0.04 J per token. Generating output costs 5.6 J per token one request at a
  time.
- **Batching is the biggest lever.** Running 64 requests at once cuts the cost
  per output token 37 times, to 0.15 J.
- **A shared prompt prefix is nearly free once cached.** In multi-turn
  conversations, growing a shared prefix from 1k to 32k tokens adds only 7% to
  each turn.

The common belief that energy is a fixed amount per token does not hold. It
depends on whether the token is input or output, how many requests run
together, and what is already cached.

## Why measure this

Systems that route queries between language models, such as the latency-aware
router in [Mind the Delay](https://arxiv.org/html/2607.18253v2), price each
query as a fixed cost per token and leave energy out. This project measures
what energy actually looks like on one edge server, as curves a router or a
planner could use. It does not build a router.

## Setup

- One NVIDIA H100 NVL GPU (95 GB), power limit set to 400 W.
- vLLM serving Qwen/Qwen3.8-27B (text only) from a Docker container,
  `vllm-qwen`, on the same machine. Prefix caching is on, the vLLM default.
- Traffic generated by `vllm-bench` with random prompts.
- The server is shared with other work, so the experiment only ever stops and
  starts this one container. It never reboots the machine or changes the GPU.

## What we measure

There are two kinds of number, and they should not be added together:

- **Levels** are power, in watts: what the server draws while sitting in a
  state.
- **Energies** are joules: the extra energy a piece of work costs on top of
  the level it started from.

| Measurement | What it is | Unit |
|---|---|---|
| Off | Container stopped, machine on | W |
| Idle | Model loaded, no requests | W |
| Load | Starting the container until the model answers | J and s |
| Prefill | Reading a prompt, by prompt length | J per request |
| Decode | Generating output, by number of requests at once | J per output token |
| Agentic | Multi-turn conversations, by shared prefix length | J per turn |

Off, idle, and load together answer a practical question: how long must the
model sit unused before stopping it saves energy?

```
  break-even time  =  load energy above off (J) / (idle W − off W)
```

## How a run works

The experiment is a list of runs, one per measured point, done one after
another in random order so that slow drift over the night does not line up
with any curve. Each run records its own power traces and the times its phases
begin:

```
  [ restart: settle → off → load ]  →  settle → idle  →  [ workload ]
     load run only                     every run         workload runs only
```

- **Settle** waits until the GPU has cooled to 45 °C. A warm GPU draws several
  watts more at rest (about 92.5 W at 43 °C against about 100 W at 59 °C), so
  every resting measurement starts from the same temperature. It is checked
  every 10 s and is not measured. Settling took 1.5 of the 3.2 hours.
- **Off** holds the container stopped for 30 s.
- **Load** runs from `docker start` until the server answers on `/v1/models`,
  which happens once vLLM reports it is ready. This took 78 s. Weights came
  from the operating system's file cache and compiled kernels from a cache
  volume, so this is a warm start.
- **Idle** holds the loaded model with no requests for 30 s. Once the GPU is
  at rest the level is flat: across all runs it stayed between 92 and 94 W.
- **Workload** runs `vllm-bench` and lasts from the moment it is launched
  until it exits, including the last requests finishing with fewer in flight.

Load is measured above its own run's off level, and each workload above its
own run's idle level. Using each run's own baseline matters for the
whole-server meter, since other things on the machine drift over the night.

## How power and energy are measured

Two meters run for the whole of every run. Both are timestamped with the same
clock, so they line up with the phase times directly.

- **GPU, 10 times a second,** through NVIDIA's management library (NVML). It
  reports power, a running energy counter kept by the GPU itself, and
  utilization, memory, clock, and temperature. Energy for a phase is how far
  the counter moved during it. Faster sampling only repeats readings.
- **Whole server, once a second,** through the server's management controller
  (`ipmitool dcmi power reading`). It reports power only, so energy is power
  integrated over time with the trapezoid rule. Faster polling only repeats
  readings. A failed poll is skipped; this cost about 0.03% of the energy.

Phases rarely start exactly on a sample, so both meters are interpolated at
each phase's start and end.

The GPU is the headline number. It is the part the workload drives, and its
meter is fast and precise. The whole-server number includes CPUs, memory,
fans, and everything else running on the machine. The GPU is only about 93 W
of the server's roughly 290 W at idle.

## The three workloads

All three are `vllm-bench` runs at one setting each. They differ in which
setting varies across runs and what the energy is divided by.

| Workload | Varies across runs | Held fixed | Divided by |
|---|---|---|---|
| Prefill | prompt length, 128 to 32,768 tokens | 1 output token, 1 request at a time, 100 requests | requests |
| Decode | requests at once, 1 to 64 | 128 input tokens, 512 output tokens, 25 requests per concurrent slot | output tokens |
| Agentic | shared prefix length, 1,024 to 32,768 tokens | 20 conversations of 8 turns, 128 tokens in and out per turn, 1 at a time | turns |

- **Prefill** measures reading the prompt. Each request generates a single
  token, so almost all of its cost is reading input.
- **Decode** measures generating output. Each request generates exactly 512
  tokens, ignoring end-of-text, so every run does the same work per request.
  The short 128-token prompt is a small fixed overhead.
- **Agentic** imitates an agent loop. Every conversation in a run starts with
  the same prefix, standing in for a system prompt and tool definitions, and
  each turn resends the whole conversation so far. The prefix cache can serve
  most of each prompt from memory.

Prompt lengths are exact for prefill and decode, which send token IDs
directly. Agentic needs the chat interface, which wraps text in a template, so
its lengths are approximate. Each run uses a fresh random seed so that prompts
never repeat between runs and the cache only helps within a run.

## Results

Run on the night of 2026-10-26/27: 23 runs over 3.2 hours, with no failed
requests.

| | GPU | Whole server |
|---|---|---|
| Off | 64 W | 256 W |
| Idle | 93 W | 295 W |
| Load above off (78 s) | 4.1 kJ | 10.3 kJ |
| Break-even idle time | 140 s | 266 s |
| Prefill J/request, `a + b·L + c·L²` | 5.2 + 0.036·L + 2.4e-7·L² | 5.1 + 0.037·L + 8.8e-7·L² |
| Decode J/token, `a + b/n` | 0.063 + 5.5/n | 0.079 + 6.9/n |
| Agentic J/turn, `a + b·p` | 743 + 0.0016·p | 940 + 0.0017·p |

*L* is prompt length, *n* the number of requests at once, and *p* the shared
prefix length, all in tokens. Each curve is fitted to minimise relative error,
since its values span several orders of magnitude. Prefill needs the squared
term: a straight line misses the longest prompts by 11%.

What the numbers show:

- **The GPU runs at its 400 W limit for almost every workload.** Energy
  therefore tracks time. Anything that gets more work done per second, such as
  batching, lowers the energy per token.
- **Prefill costs about the same per input token past 1k tokens.** Per
  token it falls from 0.079 J at 128 tokens to about 0.038 J at 2–4k, as
  fixed costs spread out, then rises to 0.043 J at 32k as attention over long
  contexts grows.
- **Decode follows `a + b/n` closely.** Most of the cost of one request at a
  time is shared when requests run together. It is still falling at 64, so
  the floor `a` of about 0.06 J per token is extrapolated.
- **Agentic turns cost about what their output costs.** A turn costs about
  743 J, close to 128 output tokens at the one-at-a-time decode rate (5.6 J
  each). Growing the shared prefix from 1k to 32k tokens adds only about 50 J
  per turn. Reading 32k tokens without the cache costs about 1.4 kJ.
- **The rest of the server adds about a quarter** on top of the GPU's extra
  energy for each workload. For load, the whole server uses 2.5 times what
  the GPU does.
- **Stopping the model is worth it after a few minutes unused:** about 140 s
  counting the GPU alone, or 266 s for the whole server. Restarting costs
  78 s of waiting.

`uv run scripts/plot.py` draws each curve with its fit, the power trace of
the restart, and a timeline of every run.

## Limits

- **Each point was measured once.** There is no error bar on any number.
- **Whole-server figures for short prompts are rough.** Prefill runs up to
  1,024 tokens last 6–15 s, against a meter read once a second.
- **The decode floor is extrapolated** beyond 64 requests at once.
- **Off means the container is stopped, not the machine.** The server cannot
  be rebooted.
- **Loads are warm.** A cold start, reading weights from disk and compiling
  kernels, would cost more.
- **Nothing else on the server changed its load during the run.** This was
  assumed, not checked, though the idle level stayed flat all night.
- **One GPU, one model, one power limit.** The coefficients describe this
  configuration.

## Out of scope

- Money or cost modeling; only joules and watts.
- Splitting a batch's energy among the requests in it. The hardware has no
  per-request energy counter.
- Routing or choosing between models.
- Multiple GPUs, servers, or serving instances.
- Images, audio, and other inputs beyond text.

## Future work

- **Dense against mixture-of-experts models, and quantization,** where energy
  may stop tracking the amount of computation. Each is a new container and a
  new experiment file.
- **Another size of Qwen,** to test whether the coefficients transfer: the
  concurrency term should move while the per-token floor should not.
- **The power limit as a variable,** between 200 and 400 W.
- **Comparing model families,** such as Qwen against Gemma. Families also
  differ in training data, tokenizer, and size, so a fair comparison needs
  care.
